# gh-post: constraints, rejected alternatives and rationale

## Rationale

- **Rationale: A gh api call is a read only in a plain form.**
  gh sends a call holding a field as `POST` unless `-X GET` says otherwise, so a field without it makes a write. A GraphQL query and a mutation are both sent with `POST`, so only the operation tells a read from a write there, and a query the reader cannot see, such as one read from a file, might be a mutation.
  Evidence: "The default HTTP request method is GET normally and POST if any parameters were added", overridden by `--method`, and a GraphQL query is sent through the `query` parameter, https://cli.github.com/manual/gh_api

- **Rationale: A command that mentions no gh post verb sends no post.**
  The post hooks, prose's and the inquisitor's, catch accidents in the common ways an agent posts on an issue or pull request, in a Discord message, or with linear-app on a Linear issue; they cannot stop an agent set on posting in a way neither hook reads: such an agent can run gh from a script file, through a gh alias, or from a program git runs because of repository configuration set in an earlier tool call, none of which a command line shows. No list could catch every form, so the closed list of gh post verbs holds only the common ones: the `gh pr` and `gh issue` verbs that post, `gh api` calls that are not reads, discord-bot's `post`, `edit` and `thread`, and linear-app's `post` and `edit`. A line that mentions none of them passes both hooks unread, and only the instructions of the skills that post, such as prose and the inquisitor, cover what it posts: `gh pr merge --body`, `gh release` notes, `gh discussion` posts, project draft issues, agent-task descriptions, gists, label descriptions, gh aliases and extensions, and gh run through a variable such as `$X pr comment`. Such a form is blocked, as unreadable, only when its words happen to mention a gh post verb, as `gh pr merge 5 --body 'edit docs'` does, its body's `edit` following `gh` and `pr`. Code given to a data command, such as `python3 -c` or `git -c`, passes even when it mentions a post verb, since the data-command rule lets it through.
  Evidence: a `PreToolUse` hook sees a tool call's command line, never what a program it starts sends, https://docs.anthropic.com/en/docs/claude-code/hooks; `gh alias set` maps a name to any gh command, https://cli.github.com/manual/gh_alias_set; git runs a repository's hooks, https://git-scm.com/docs/githooks, and the command `core.fsmonitor` names, https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsmonitor

- **Rationale: Another Linear write tool sends no post only when it holds no text.**
  Among the string keys of the Linear MCP's `save_`, `create_`, `update_` and `submit_` tools, other than `save_comment` and `save_issue`, the no-text list holds each key whose schema describes an ID, a reference to an existing thing by its name, a status, an enum value, a date, a commit or a colour. On these tools, `title` and `name` are off the list but read as titles, and `summary` and `description` as Linear summary text, bodies in which the inquisitor's post hook refuses any question since no answer service reads them (inquisitor spec: *A question in Linear summary text is refused*), wherever they sit in a call, a `links` item's `title` included, since they hold text a person reads on whatever the call saves (on these tools `name` names the thing the call saves, not an existing thing). Every other string key off the list makes the call unreadable: other text a person reads (`body`, `content`, `subtitle`, a `links` item's `url`, which Linear shows as the link, and the strings inside `patch` and `anchor`); a file (`base64Content`, `filename`, and `assetUrl`, which names a file the agent uploaded; the file's URL or name becomes the attachment's title by default, a title the reader cannot see in the call); a string whose schema gives it no format or allowed values, such as `icon` ("Icon name or emoji code") and `version` ("Version identifier"); and `sha256` and `contentType`, which come only with `base64Content`, so putting them on the no-text list would change nothing: a call holding them holds `base64Content`, which already makes it unreadable. Judging keys rather than tool names lets a text-free call, such as a project's state change, through. It also makes unreadable a call holding a string under a key missing from the list, including one a later version of the server adds, so a new text field cannot pass unread. The Linear MCP's tools with other prefixes (`delete_`, `merge_`, `share_`, `unshare_`, `resolve_`, `mark_`, `retire_`, `restore_`, `prepare_`) take only IDs, enum values, dates and upload details that Linear shows nowhere as text, so the reader reports their calls as sending no post; `prepare_attachment_upload`'s suggested title reaches Linear only through `create_attachment_from_upload`, which the list judges.
  Evidence: the input schemas of the Linear MCP's tools, `save_document`, `save_status_update`, `save_diff_comment`, `save_project`, `save_milestone`, `save_issue_label`, `save_project_label`, `save_release`, `save_release_note`, `create_attachment`, `create_attachment_from_upload`, `create_issue_label`, `update_diff` and `submit_diff_review` among them, as the server served them to Claude Code on 2026-11-27, read through ToolSearch's `mcp__linear__*` definitions, https://mcp.linear.app/mcp; the server's tool list is described at https://linear.app/docs/mcp

# sequencer: constraints, rejected alternatives and rationale

## Rationale

- **Rationale: An issue takes the place of an open pull request tied to it.**
  An item that comes after an issue comes after every pull request tied to it, because it needs all of the issue's work. The script can make it wait only on pull requests tied to the issue, so every pull request doing part of that work needs a tie. The cost is that the item also comes after a second pull request competing to close the issue. A pull request that does only part of an issue's work cannot say `Closes`: GitHub would close the issue when that pull request merged. Without a `Part of` line, nothing would tie it to the issue. A `Closes` line is read as text too, because GitHub makes no closing reference for a pull request whose base is not the default branch, such as a stacked pull request. Prose that names the issue ties nothing, because prose also names issues that a pull request only mentions.
  Evidence: issue #107's work was split across pull requests #108, #109 and #110, two of them calling themselves a part ("Implements the docs part of #107", "the hook half of #107") and none saying `Closes #107`, so GitHub never closed #107: it stayed open three days after the last of them merged, until closed by hand, https://github.com/adamstallard/shared-skills/issues/107#issuecomment-7140641196, https://github.com/adamstallard/shared-skills/pull/108, https://github.com/adamstallard/shared-skills/pull/109, https://github.com/adamstallard/shared-skills/pull/110, https://github.com/adamstallard/shared-skills/issues/107
  Evidence: GitHub's documentation says closing keywords are "interpreted only when the pull request targets the repository's default branch", and that for a pull request into any other branch "these keywords are ignored, no links are created", https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue

- **Rationale: A pull request tied to no issue is listed.**
  Without the listing, a pull request that does an issue's work but names the issue in no `Closes` or `Part of` line would go unnoticed, and the issue would stay open after the work merged.
  Evidence: pull requests #108, #109 and #110 did the work of issue #107 and named it only in prose, so GitHub never closed #107: it stayed open three days after the last of them merged, until closed by hand, https://github.com/adamstallard/shared-skills/issues/107#issuecomment-7140641196, https://github.com/adamstallard/shared-skills/pull/108, https://github.com/adamstallard/shared-skills/pull/109, https://github.com/adamstallard/shared-skills/pull/110, https://github.com/adamstallard/shared-skills/issues/107

- **Rationale: The script reads OpenSpec changes only through the OpenSpec CLI.**
  If the script parsed OpenSpec's markdown itself, a release that changed the format would leave the script silently wrong. Read through the CLI, as spec-check and spec-trace read it, such a release makes all three fail their tests instead.
  Evidence: OpenSpec's own reading of the same markdown changed in both 1.16 releases, which a hand-written reader would have had to track. In 1.16.0, a line beginning with inline code written in triple backticks (```` ```npm test``` ````) stopped being read as the opening of a code fence, which had hidden every requirement after it, https://github.com/Fission-AI/OpenSpec/releases/tag/v1.16.0 (Fission-AI/OpenSpec#2131)
  Evidence: in 1.16.1, section headings with a closing `#` run, such as `## ADDED Requirements ##`, began to be read the same as unclosed ones (Fission-AI/OpenSpec#2205), and a requirement under an unrecognized `## … Requirements` section, once silently dropped, began to be refused (Fission-AI/OpenSpec#2207), https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md#1161

- **Rationale: The model step orders changes whose code calls each other's code.**
  This explains the requirement's limit on what the script takes from the model step: only edges between items, each with a reason. The model step reads changes' files, which can carry text a writer copied from anywhere, so that text can steer the model. If the script took whatever the model step returned, that text could steer anything the script publishes. With the limit, a misled model can only add a wrong code-calls-code edge or leave out a real one, and write each edge's reason. A wrong edge misplaces a recommendation and merges nothing, since the sequencer never merges. A reason is written as inline code (*Text from a pull request or the model is written inert*), so a misled model's reason renders no mention or link.
  Evidence: OWASP ranks prompt injection first among risks to LLM applications, including indirect injection, where instructions hidden in files a model reads alter what it outputs, https://genai.owasp.org/llmrisk/llm01-prompt-injection/

- **Rationale: A link to an outside item is listed as not counted.**
  A link that made an item wait until another repository's item closed would make this repository's work wait on people who have not agreed to be in its order: they may close, reopen or abandon their item without knowing that anything waits on it. The script often could not read the other item either: a private repository, a missing item and a refused token all return the same not-found answer, so it would make work wait on a guess. Listing the link loses little: the order's line still names it, and for a "blocked by" relation GitHub also marks the issue as blocked on the repository's Issues page. Two repositories whose work really depends on each other need an order that holds both, where the link is an ordinary edge; this order holds one repository. The cost is that an item blocked by outside work appears in the order as if ready, with the link beside it.
  The order's issue writes the outside item, on the linking item's line only, as plain `owner/repo#number` text rather than inline code, which GitHub renders as a link, so a reader can open the item. The cost is that GitHub adds a `cross-referenced` event to the outside item's timeline, in a repository this order does not cover. GitHub adds one such event for each item that refers to the outside item, not one for each edit, so the order's issue adds a single entry however often a run rewrites its body.
  Evidence: GitHub's REST documentation says that for a request to a private resource that is not properly authenticated, "GitHub uses a `404 Not Found` response instead of a `403 Forbidden` response", https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource
  Evidence: GitHub's documentation of issue dependencies says "Blocked issues are marked with a "Blocked" icon on your project boards or repository's Issues page", https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies
  Evidence: GitHub's documentation of autolinked references lists "`Username/Repository#` and issue or pull request number" among the references that "are automatically converted to shortened links", https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls
  Evidence: measured on 2026-11-19 UTC with gh 2.103.2, on pull request adamstallard/shared-skills#25, whose timeline the issues API serves. `gh api repos/adamstallard/shared-skills/issues/25/timeline --paginate`, filtered to `cross-referenced` events, listed 19 events from 19 source items, one each. Two of the sources are adamstallard/igor#247 and adamstallard/igor#211. By `userContentEdits` in GitHub's GraphQL API, #247's body named #25 from the start and was edited twice more, and #211's body gained the reference in an edit and was edited three more times, each edit keeping the reference, https://github.com/adamstallard/shared-skills/pull/25
  Evidence: GitHub's documentation of issue dependencies says of `gh issue view` that "The output includes "Blocked by" and "Blocking" rows when relationships are set", https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies

- **Rationale: With an API key, the model step is one API call with no tools.**
  The model step reads changes' files, which can carry text a writer copied from anywhere, so that text can steer the model. A model can act only through the tools a request offers it: with none offered, a steered model can only return text, and the script takes from that text no more than validated edges. Run as an agent with tools, the same model could be steered into running commands or making requests with the run's credentials.
  Evidence: Anthropic's tool-use documentation says Claude calls functions "that you define or that Anthropic provides", returning "a structured call that your application runs (client tools) or that Anthropic runs (server tools)", https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview
  Evidence: OWASP ranks prompt injection first among risks to LLM applications, including indirect injection through files a model reads, https://genai.owasp.org/llmrisk/llm01-prompt-injection/

- **Rationale: The workflow runs no code from a pull request.**
  The template triggers on `pull_request_target`, whose runs hold a token that can write to the repository, and the repository's secrets. Code from a pull request's head, run in such a run, would get both, so anyone who opens a pull request, from a fork included, could write to the repository or read its secrets.
  Evidence: GitHub Security Lab shows that a `pull_request_target` workflow has write permission and secrets, and that checking out and building an untrusted pull request in one lets its author run code with them, https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/

- **Rationale: The whole order lives in one issue's body.**
  A reader who opens an issue with `gh issue view`, the default, sees its title and body and none of its comments, and an agent's piped `gh issue view --comments` prints the comments without the body. An order kept in comments would be missing from the default read, and one kept in the body is missing only from the comments-only read.
  The order's issue is used only when its author has write access, because the issue's author can edit its body whatever their access, and so could rewrite the cycle overrides and stored code edges kept there. An installed App's bot account may be its author, since an App that can open an issue can already edit any issue's body.
  Evidence: gh's manual says `gh issue view` displays "the title, body, and other information about an issue", and that "When output is piped or redirected, only the comments are printed" with `--comments`, https://cli.github.com/manual/gh_issue_view
  Evidence: measured on 2026-11-10 UTC with gh 2.103.2, on an issue whose body is 2521 bytes and which has one comment. `gh issue view 168 --repo adamstallard/igor | wc -c` printed 2803 bytes: the title, metadata and body. `gh issue view 168 --repo adamstallard/igor --comments | wc -c` printed 164: the one comment with its author header, and no title or body, https://github.com/adamstallard/igor/issues/168
  Evidence: GitHub's REST documentation for updating an issue says "Issue owners and users with push access or Triage role can edit an issue", which the roles table below shows does not let Triage edit titles and bodies, while its "Issue owners" are the issue's authors, https://docs.github.com/en/rest/issues/issues#update-an-issue
  Evidence: GitHub's list of the permissions each REST endpoint needs gives a GitHub App the "Issues" repository permission at write level both to create an issue (`POST /repos/{owner}/{repo}/issues`) and to update one (`PATCH /repos/{owner}/{repo}/issues/{issue_number}`), https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-issues
  Evidence: GitHub's table of repository roles gives "Edit anyone's issue titles and bodies" to the Moderate, Write, Maintain and Admin roles, and not to Read or Triage, so of those without write access only the issue's author can edit its body, https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization

- **Rationale: The script edits only the text between its markers.**
  A new block goes above the prose skill's `prose ✓` footer and changes the text that footer hashes, so the footer stops matching. That is harmless. The only posted body prose's hook fetches is a pull request's, when an agent hands the pull request back for review, and it reads only whether the footer says the body's cold read was put off until then, never the hash. An issue body, such as the order's issue, it never fetches.
  Evidence: prose's hook fetches a body only for a pull request being handed back, and calls only `deferred_footer(body)` on it, [.agents/skills/prose/scripts/prose.py:1560-1561](https://github.com/adamstallard/shared-skills/blob/528ae4ec/.agents/skills/prose/scripts/prose.py#L1560-L1561)

- **Rationale: The workflow recomputes the order on GitHub events and once a day.**
  Pull request events trigger through `pull_request_target`, not `pull_request`, because a `pull_request` run for a fork's pull request gets a read-only token, which cannot edit that pull request's body. `pull_request_target` has no activity type for a submitted review, so review events come through `pull_request_review`, whose run for a fork's pull request may get a read-only token and publish nothing; the next run with a write token publishes the order.
  Evidence: GitHub's documentation of workflows in forked repositories says a `pull_request` run from a fork gets a read-only `GITHUB_TOKEN`, https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflows-in-forked-repositories
  Evidence: GitHub's documentation lists the activity types of `pull_request_target`, none of them a submitted review, https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#pull_request_target

- **Rationale: The script prints the order for callers without editing anything.**
  Beside `order`, which edits nothing, `publish` in a session edits the bodies directly, rather than dispatching the workflow, because a dispatch runs only a workflow file on the default branch, so a repository without the workflow could not publish from a session at all. The cost is that a session's write is outside the workflow's concurrency group, so it can overlap a workflow run, and the later write wins: code edges that only the overwritten publish wrote are lost until they are published again.
  Evidence: GitHub's documentation of `workflow_dispatch` says the workflow file must be on the default branch to be triggered, https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_dispatch

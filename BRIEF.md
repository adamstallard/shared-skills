# Brief: the inquisitor's answer-session UI (continue the prototype)

You're continuing a UI prototype with Adam. Read this, then load the mod and ask him what to change.

## What it is

The **answer session** is part of the `inquisitor` skill in adamstallard/shared-skills (spec: PR #25, branch `spec/inquisitor`, `openspec/changes/inquisitor/`; read it with `gh pr view 25 --json title,body,comments`). The inquisitor filters every question an agent is about to ask a person; questions that survive are relayed from subscribed channels (GitHub repos, Linear teams, Discord channels), asked by agents running the inquisitor or by people. In an **answer session** the user does nothing but answer them, in one immersive UI; each answer is posted back by a per-surface personal relay app account, prefixed "User says: ". Replies or mentions directed at the relay account count as new questions.

The UI is a **Claude Code mod** (plugin with a hooks module). This is a prototype with made-up questions; nothing is posted.

Non-UI parts of the answer session — subscribing to channels, finding questions asked of him, relay accounts, setup — go through the normal spec PR → implementation PR process, separately. Don't write requirements about layout or interaction.

## What's built (and why)

- **The band above the prompt, full width, in every layout** (Adam, 2026-10-20). Adam launches Claude Code from JetBrains' session picker, whose background sessions always draw in the fullscreen layout, so fullscreen is the layout that matters. A pane can't be kept out of the fullscreen sidebar (it docks from 110 columns at ~45% of the width), so the answer session draws in the `AbovePrompt` band instead: a `ui.render` hook, no `$.ui.open`. The band is the terminal's width less the engine's 5-column `[-]` mark, in fullscreen and on the main screen, at any width. In fullscreen its height is what half the terminal leaves above the prompt (15 rows at 40, 10 at 30, 20 at 50, 7 at 24; a taller prompt box takes rows from it); on the main screen the engine offers the terminal's height, so the band takes the screen less the prompt box, its rules and the footer.
- **Clicks**, in fullscreen (the main screen reports none): the progress dots open that question; `summary` after them opens the summary, and each summary row opens its question; an option puts its number in the prompt box (the preview and the hint line then show what Enter relays). There is no Relay or Send button (Adam: Enter already does it); every key-row command does what its letter and Enter do; `o: show the original` and `c: reply by citing it` beside the question do the same; the source (`adamstallard/igor #216`) is a `Link` the terminal opens. A click presses without taking the keyboard: typing stays in the prompt box (verified in tmux).
- **All input is in the prompt box, Enter confirms** (Adam, 2026-10-20). `intent()` reads the box's text against the screen: a digit chooses an option, one letter is a command (the key row lists them: `t` talk to Claude (`h` help me answer where there are no suggestions), `w` won't answer, `l` later (comes back after the new ones), `a` agree with a suggested verdict, `c` cite, `o` original, `r` reopen, `e` edit, `b`/`n` back/next, `q` quit; in a discussion `r`, `a`, `b`; while choosing why not to answer, the digits 1–3 and `b`; then, for reason 3, the digits 1–4 for the filter, the place for filter 1 (and `t` or `h`), and `p` to post without a note), anything longer is an answer, or in a discussion a message to the model. The band previews it live from a copy of the box (`prompt.edit` and `prompt.change` hooks into `$.state` `prompt`). The `prompt.submit` hook does it and drops the prompt, so nothing but a discussion message reaches the model; its drop reason is a row in the transcript (`Prompt dropped by a hook: Relayed to GitHub …`), which makes the conversation above the band a log of what was done. Only the person's own prompts (origin `composer`) are read; slash commands, the engine's own prompts and any other origin pass. The hint line under the prompt says what Enter would do (`⏎ relay to GitHub`, a refusal's reason, or what to type).
- **Opening and closing**: `/answer` toggles; `q` and the key row's `(q)uit` close it. Closing keeps the queue and everything done, and `/answer` reopens where it was. Closed, prompts reach the model as usual. While a survey holds the band the session yields it, and Enter answers nothing (it says so) until the survey is gone.
- **Fitted to the height**: every row below the bar is built as exactly one terminal row, so a view counts what it draws and gives things up in a fixed order (`TRIMS`) until it fits: the minor gaps, the "Choose an answer" label, the space between options, the log note, the own-words row, effects to one line, context to one line, the related decision, then Adam's three gaps (above the question, above its context, above the choices, the last kept longest), provenance to one row, what was asked of the asker, the post preview to two lines, effects, context, the preview to one row, provenance. The question, the options' labels and the post's first line stay; nothing scrolls. Gaps are named (`GAP_ORDER`); rows left over go to them in that order, a row each, then a second each, so spare height spaces the view out instead of pooling at its foot.
- **The question view**: a bar (`Answer session`, the dots — ● relayed, ◐ for later, ○ new, ◉ current, ◇ in a conversation, ◌ waiting for the asker, ⊘ won't answer, ◎ answered for you, ◈ handled for you or by your choice — `summary`, "1 of 9" and the tallies: all of them from 120 columns, only those above zero below it, and only on the summary; the build at the right), a rule above the bar when the band has 14 rows or more (it parts the band from the conversation), the body, and a key row (its commands, then the last thing done or why Enter would refuse, then `q: close`). From 100 columns the body is two columns: the question on the left (47%: source and link, age, asker; the question in bold; context; the asker's reply; related or "possibly answered"), a thin rule, and the work on the right (the options as blocks, `1: Label` bold, ★ recommended on the first, a dim `→ effect` under each; "Or type your own answer in the prompt box", or for a person "Reply to <name>"; the preview of exactly what posts, once something is chosen or typed, in one run that wraps when long: "POST ON GITHUB AS adam-relay[bot]: User says: …"). A short wide strip reads better side by side than in one tall column, and the options sit beside the question they answer. Under 100 columns it is one column, the same pieces stacked.
- **Talking to Claude** (`t` or `h`; Adam, 2026-10-20): the discussion is the session's own conversation, above the band. A message typed during a discussion goes on to the model as an ordinary prompt with the question attached as `context` (`discussionContext()`: the question, where and by whom, context, options with effects, the related or possibly-answering decision, the asker's reply, and how to help: explain, lay out trade-offs, ask back, don't choose for him, plain terminal text under ~120 words unless he asks for more, read with tools but post or change nothing). So the model can read the thread, the code and the specs before it answers (seen in tmux: it ran `gh pr view` on igor #216), and its reply renders in the transcript. The band keeps the question and its options in view, says where the discussion stands ("Claude is answering above…", a turn that ended without a reply; no message count, and no echo of what is typed, which the prompt box and hint line already show), and shrinks to that (8–10 rows), so the conversation gets the rest of the screen. Digits and one-letter commands still act in the session and are dropped: a digit chooses that answer (and relays on Enter), a letter that is no command is refused, a second message while a reply is under way is refused. The queue resumes exactly where it was. `b` goes back to the question unchanged.
- **Keys are written with the letter inside the word** (Adam, 2026-10-20), everywhere: `(t)alk to Claude`, `(w)on't answer`, `(l)ater`, `(a)gree`, `(b)ack`, `(n)ext` (side by side on the keyboard; in a discussion or while choosing why not to answer, `go (b)ack` returns to the question), `(c)ite the decision`, `(o)riginal`, `(r)eopen`, `(r)eview those for later`, `(e)dit your post` (`(e)dit the post` or `(e)dit the reply` on one the session posted), `(p)ost it` (answering for the inquisitor without a note), `(q)uit`; only the digits keep `1–2: choose` (`1–3: choose why`, `1–4: choose the filter`). `(q)uit` closes the answer session, not Claude Code. Below 100 columns the key row's commands sit two columns apart instead of three, so the longest row (`(h)elp me answer (c)ite the decision (w)on't answer (l)ater` and the three at the right) fits 95 columns; the status gives way to the commands, never the reverse.
- **Claude drafts the reply on request** (Adam, 2026-10-20): the mod registers a tool, `mcp__answer-session__propose_reply` (`isDeferred: false`, so it is in the model's tool list), and each discussion message's context tells the model to call it when Adam asks it to write or draft his reply. The tool posts nothing: it returns the band to the question view with the draft in the prompt box, where the band previews the post and Enter relays it after any edit; `(t)alk to Claude` goes back to ask for changes. Verified with the real model in tmux on Maya's question: it called the tool unprompted by name, and the draft showed as the post preview with `⏎ relay to Linear`.
- **The help command is named for the question** (Adam, 2026-10-20): `(t)alk to Claude` on a question with suggested answers, `(h)elp me answer` on one without, `(h)elp me edit` while editing a post. Each opens the same conversation ("TALKING TO CLAUDE"), where free-form messages ask about the question, have Claude draft the reply, or both. On the question view a single letter that is not a command is refused, never relayed.
- **Drafting works for an edit too** (Adam, 2026-10-20): while editing a post, the talk command is offered; each message tells Claude what the post says now; its draft lands in the prompt box with the edit still on, previewed as `EDIT ON …`, and Enter updates the post. Rewording and asking the asker are not offered during an edit.
- **Editing a post** (Adam, 2026-10-20): on a relayed answer or a question waiting for the asker, `(e)dit your post` puts what was posted in the prompt box; the band shows the post and previews `EDIT ON GITHUB AS …: User says: …`; Enter updates it (marked `edited`), `(k)eep it as posted` drops the edit, and moving to another question drops it too. The real skill edits the relay's own comment or message (GitHub, Linear and Discord all allow it), so it keeps each post's ID.
- **`(b)ack`, `(n)ext` and `(q)uit` always sit at the right end of the key row** (Adam): the same place on every screen, for quick back and forth by click.
- **Links** wherever they lead somewhere: the question's source, the related decision, "possibly answered", a relayed post (`view`) and an asker's reply. A plain click on a link does nothing in fullscreen; ctrl-click (or a terminal-kept cmd-click) opens it: verified in tmux with a stand-in `open` on `PATH`, which Claude Code ran with the link's URL. Prototype URLs past the thread's own are made up.
- **The discussion band's commands** (Adam, 2026-10-20), the key inside the words (no key for continuing: typing does that, Adam 2026-10-20): `(r)eword the question` (once Claude has replied: the question rewritten from the talk, answered at once), `(a)sk the asker` (you can't answer without clarification from them: their question waits for the reply), `go (b)ack` (answer it as it is). A digit doesn't answer while talking (the choices are on the question, not shown here): it says to go back. No message count. For an agent's question, a reply reaches whichever worker next takes the item (PR #25: an Igor worker asks in its handback and is gone), so asking back is mostly for people's questions.
- **The discussion's record**: each question's turns are kept in `$.state` `talks`. The submit hook records the message, marks the question `thinking: reply` and queues `{ id, text }` in `awaiting`; `turn.start` binds the turn whose text matches (or, failing a match, the oldest waiting message) to that question in `replyTurns`; `turn.complete` on the main loop records the turn's final text as the reply, or an error turn when it was interrupted or failed. `r` (rephrase and ask again, marked "↻ Rephrased after your discussion", `o` shows the original; the real skill would log the rephrasing and a one-line summary with the answer) and `a` (ask the asker) read that record and run on `$.model.complete` with the question as the system prompt (`systemPrompt()`).
- **Ask the asker** (`a`, from the discussion): the model drafts a clarifying question into the prompt box (only into an empty one), to edit there; the band previews the post; on Enter the question is marked waiting and the queue moves on; the prototype simulates the reply after ~25 s and the question returns with the reply quoted (and revised options for agent questions). Beside an asker's reply the context gives way first; the reply is never cut.
- **What fills the screen above the band**: the session's conversation, never hidden: the discussions, and a row for everything Enter did. On the main screen the question view's band covers the screen and the discussion's band is short, so a discussion's replies show above it there too.
- **Summary**: the head ("All caught up." / "Nothing new. 1 for later." / "n questions still new"), relayed of total with how many were answered and handled for Adam, how many he answered for the inquisitor (their rows marked `you chose · `), how many he won't answer and how many wait, and a row per question with something done to it in queue order (glyph, asker, where, what was posted with its prefix, or the won't-answer's reason, aligned), each a click away; `r` reviews the deferred.

## Known limits

- Clicks reach a mod only in the fullscreen layout; on the main screen nothing in the band responds, and a `Link` is a terminal hyperlink the terminal itself may open. Not tried here: a click on the source link (it would open a browser on the machine).
- In fullscreen the band gets at most what half the screen leaves: 15 rows at 40. At 24 rows (7 band rows) and fewer the question view drops its source and asker.
- The band's `[-]` (or ctrl+x ctrl+a) collapses it to `▸ plugin panel hidden`; the mod is not told, so Enter still acts on the question while it is collapsed, and the drop row says what was done.
- After a dropped prompt the engine puts its text back in the box (a `prompt.change` with origin `engine`). The submit hook records what the box should hold instead (nothing, or a citation `c` put there); the change hook applies it when the put-back arrives, or `PUT_BACK_MS` later. The mod's own `$.prompt.fill` skips its own change hook, so `putInBox` updates the copy itself.
- A discussion reply is bound to its message by the turn's text; a message delivered into a turn already running would share that turn's reply. Refusing a second message while a reply is under way keeps that from happening.
- The discussion grows the session's own context: every discussion message carries its question block.
- usage-hint's `tail` still draws after the hint line; it shows nothing on API billing. The engine keeps its permission pill (`⏵⏵ auto mode on`) in that line; the separate `SessionMode` label draws nothing while the session is open.
- Resizing the main screen in JetBrains' 2025 terminal leaves overlapping frames on the left (Adam, 2026-10-20). tmux redraws cleanly, so it is most likely how that terminal re-wraps lines; untested against a plain session without the mod.
- An Enter on an empty prompt box never reaches a mod (seen in tmux), so the band can't take a bare Enter: posting for the inquisitor without a note is `p` and Enter.
- Tests can't raise `prompt.edit` or `prompt.change`, and a test hook can't call `$`: the live preview is untested. Tests drive Enter through `$.prompt.submit` and a model turn through `$.turn.start` and `$.turn.complete`.
- The host's scan refuses `$` passed through a value (`cmd.run($)`) or to a function whose name is reused: commands are data, and `runCommand` (from a click, `pressKey`) dispatches them.
- A mod's own calls skip its own hooks.
- A hot reload clears timers (a simulated asker reply pending during a reload stays waiting).
- Not hideable: the prompt box, toasts, permission and AskUserQuestion dialogs, a status line, the drop rows.
- Desktop and mobile surfaces are out of scope for now.

## Decided for the non-UI spec (Adam, 2026-10-20)

Not built here; these go into the answer session's OpenSpec change, which Adam will have an agent write once the open points below are settled.

- **Configuration:** an answer-session section in the inquisitor's config, `~/.config/shared-skills/inquisitor.json` (PR #25 puts the GitHub login and lore repositories there): subscriptions (GitHub repositories or organisations, Linear teams, Discord channels) and, per surface, a reference to the relay identity. Tokens stay with the github-app and linear-app skills.
- **Setup is a view in the answer session** (UI, so it is prototyped here): shown instead of the queue when that section is missing or incomplete; lists candidates (repositories from `gh`, Linear teams) to toggle, checks each relay identity can post, writes the JSON, which stays hand-editable; `/answer setup` reopens it.
- **State:** an answer's durable record is the relay account's reply in the question's thread. Answered and waiting-for-the-asker (the relay's last message is the clarifying question) both come from the threads, updated by polling. When a question comes on screen and its channel's last poll is over about a minute old, the session fetches the thread's replies since the question and shows them all; the relay's own reply marks it answered, other replies are left to Adam. Relaying checks the thread once more. Local state lives in `${XDG_STATE_HOME:-~/.local/state}/inquisitor/answer-session/`: deferrals, discussion records and poll positions, all per machine (a deferral on one machine shows as new on another; personal working state, not records).
- **Reopening lands where you left off** (Adam, 2026-10-20): the question on screen is kept in the state folder with the rest, so `answer` and `/answer` reopen on it even after Claude Code restarts; answered and waiting come from the threads.
- **One answer session per machine:** a lock in the state folder naming its holder (session name, background or not, start time), refreshed by it so a crashed holder's lock goes stale. A second `/answer` says which session holds it and offers to attach to it or take over. No TLA+ model: one person, one writer per machine.
- **A rephrased question** is logged with its rephrasing and the discussion's one-line summary in the question's log file, in PR #25's single log-file format (new fields, if needed, go into that format's requirement).
- **The relay keeps each post's ID,** so an answer or a question to the asker can be edited later where it was posted.
- **Reading uses Adam's own credentials** (his `gh` login, his Linear token, his Discord identity); relay accounts only post.
- **A relay check that fails keeps that surface off:** setup shows the failure and how to fix it, saves the rest, and leaves that surface's channels off until a recheck passes.
- **Discord is in the first version,** through PR #1's `discord-bot` skill (a named bot identity per role, no service to run), which Adam will merge first. The Discord relay is a `discord-bot` identity.
- **Polling, not webhooks:** webhooks need a public HTTPS server and Discord's push a permanent connection, both services to run; GitHub's notifications endpoint answers conditional requests that don't count against the rate limit and sets the interval (usually 60 s).
- **Won't answer, answered for you, handled for you** (Adam, 2026-10-20; the UI is built here, these parts are not): a won't-answer is local state, per machine. Reason 1 marks the thread ended so later replies there stop counting as questions; reason 2 (not a question, picked up by mistake) writes a lesson candidate against how the question was found; reason 3 posts the chosen filter's reply for the inquisitor and logs a miss against that filter, Adam's note as its "what was said". The session runs filter 1 on incoming questions and answers from a recorded answer with authority (`Recorded answer: ` and the citation); for an agent's question that clearly fails filter 2, 3 or 4 it posts that filter's action (`Inquisitor: `, naming the filter) and logs a miss; for a person's it only suggests the verdict.
- **Polling runs only while an answer session is open:** about every 60 s, with a catch-up poll on opening; nothing runs in the background.
- **A question asked of Adam** is any of: an @-mention of him in a subscribed channel (agents running the inquisitor included), a reply to or mention of his relay account, a pull request requesting his review or an issue assigned to him, and a question file on a lore repository's questions branch addressed to him.
- **Two ways in:** `/answer` in any session, and a setup-installed `answer` terminal command that starts a session with `/answer` as its first prompt. The `INQUISITOR_ANSWER_SESSION` auto-open variable is dropped (Adam, 2026-10-20): neither way in needs it, and a session from the picker can't set it.
- **The `answer` terminal command** runs `CLAUDE_CODE_NO_FLICKER=1 claude --name Answers '/answer'`: fullscreen, in place, clickable.
- **Fullscreen is the layout designed for and launched into.** The main screen works (a person whose own session runs on it can type `/answer` and gets the same band, taller and without clicks) but gets no work of its own.
